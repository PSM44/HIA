01.00_PROPOSITO_DEL_DOCUMENTO
======================================================================

Este documento describe el ciclo de vida completo de una sesión de trabajo dentro del sistema HIA.

El objetivo es definir con claridad cómo comienza, se desarrolla y se cierra una sesión de trabajo humano–IA.

Muchos documentos dentro de HUMAN.README explican partes del sistema:

START_RITUAL explica cómo comenzar.
OPERATION explica cómo trabajar.
CIS explica cómo aplicar cambios.
RADAR explica cómo observar el sistema.
BATON explica cómo mantener continuidad.

Sin embargo, estos documentos no describen el flujo completo de una sesión.

Este documento integra todos esos elementos dentro de un único modelo de ciclo de vida.


======================================================================
02.00_CONCEPTO_DE_SESION_EN_HIA
======================================================================

Una sesión en HIA es un período de trabajo en el cual un humano interactúa con uno o más sistemas de inteligencia artificial para resolver una tarea específica.

Una sesión comienza cuando el humano decide iniciar trabajo dentro del sistema HIA.

Una sesión termina cuando el trabajo se ha completado o cuando el humano decide cerrar la sesión.

Durante una sesión ocurren varias operaciones:

interacción con IA
lectura de documentación
análisis de información
ejecución de herramientas
generación de resultados
registro de cambios


======================================================================
03.00_FASES_DE_UNA_SESION
======================================================================

Una sesión completa en HIA puede dividirse en las siguientes fases.

Fase 1 — Inicio de sesión

Fase 2 — Verificación del entorno

Fase 3 — Observación del estado del sistema

Fase 4 — Trabajo humano–IA

Fase 5 — Validación de resultados

Fase 6 — Registro y persistencia

Fase 7 — Cierre de sesión


======================================================================
04.00_FASE_1_INICIO_DE_SESION
======================================================================

La sesión comienza cuando el humano decide iniciar trabajo dentro del sistema HIA.

El humano debe seguir el procedimiento descrito en:

09.0_HUMAN.START.RITUAL.txt

El objetivo de esta fase es establecer el contexto inicial de trabajo.

Actividades típicas:

definir el objetivo de la sesión
identificar el problema a resolver
establecer el contexto del análisis


======================================================================
05.00_FASE_2_VERIFICACION_DEL_ENTORNO
======================================================================

Antes de comenzar el trabajo real es necesario verificar que el entorno del sistema se encuentra en condiciones adecuadas.

Actividades típicas:

verificar disponibilidad de herramientas
verificar estado del repositorio
verificar acceso a modelos de IA

Herramientas que pueden utilizarse en esta fase:

Check-AIStack.ps1
Start-Session.ps1

El objetivo de esta fase es asegurar que el sistema está listo para trabajar.


======================================================================
06.00_FASE_3_OBSERVACION_DEL_ESTADO_DEL_SISTEMA
======================================================================

Antes de realizar cambios en el sistema es recomendable observar el estado actual del repositorio.

La herramienta principal utilizada para este propósito es:

RADAR

RADAR permite identificar:

archivos existentes
cambios recientes
estructura del repositorio

El objetivo de esta fase es comprender el estado actual del sistema antes de modificarlo.


======================================================================
07.00_FASE_4_TRABAJO_HUMANO_IA
======================================================================

Esta es la fase principal de la sesión.

Durante esta fase el humano interactúa con uno o más sistemas de inteligencia artificial.

Actividades típicas:

formular preguntas
solicitar análisis
generar contenido
diseñar soluciones
evaluar alternativas

El humano mantiene control del proceso.

La IA actúa como herramienta de apoyo.


======================================================================
08.00_FASE_5_VALIDACION_DE_RESULTADOS
======================================================================

Una vez que la IA ha generado resultados, el humano debe validar dichos resultados.

Actividades típicas:

revisión del contenido generado
verificación de consistencia
confirmación de que los resultados responden al problema planteado

La validación es una responsabilidad humana.

La IA no puede validar su propio trabajo de manera confiable.


======================================================================
09.00_FASE_6_REGISTRO_Y_PERSISTENCIA
======================================================================

Cuando el trabajo ha producido resultados útiles, es necesario registrar dichos resultados dentro del sistema.

Esto puede incluir:

creación o edición de documentos
registro de decisiones
actualización de archivos

El objetivo es asegurar que el conocimiento generado durante la sesión no se pierda.


======================================================================
10.00_FASE_7_CIERRE_DE_SESION
======================================================================

Una vez que el trabajo ha concluido, la sesión debe cerrarse formalmente.

Actividades típicas:

revisión final de resultados
registro de cambios
actualización de logs
ejecución de procedimientos de cierre

Herramientas posibles:

Close-Session.ps1

El objetivo de esta fase es garantizar que la sesión termina de forma ordenada.


======================================================================
11.00_REPRESENTACION_SIMPLIFICADA_DEL_FLUJO
======================================================================

El flujo completo de una sesión puede representarse de la siguiente forma.

↓

Trabajo humano–IA
↓

12.10_SINGLE_OWNER
This document is the single authority for:
- formal session start;
- CONTINUE;
- checkpoint;
- project switch;
- formal close;
- degraded close;
- handoff;
- evidence and confidence status;
- exact continuation instructions.

Other HUMAN documents may reference or derive summaries from this contract but
must not maintain competing lifecycle doctrine.

12.20_FORMAL_START
A formal session starts when the user invokes CONTINUE for a project.

Default:
- one active session per project;
- project identity and current state are loaded before execution;
- applicable context policy is identified;
- evidence freshness and confidence are surfaced;
- the next action must be executable or explicitly blocked.

12.30_CHECKPOINT_AND_SWITCH
A checkpoint records verified progress without pretending the session is closed.

A project switch requires:
- checkpoint or close of the current project;
- explicit target project;
- no context contamination between projects;
- loading the target project's identity, state and context policy.

12.40_CLOSE_TRIGGERS
HIA must propose or require closure when:
- the current action is completed;
- the user changes project;
- a checkpoint is reached;
- context quality degrades;
- the workday ends;
- the user requests closure;
- a blocker prevents safe continuation.

12.50_REQUIRED_CLOSE_TAXONOMY
Every formal close must classify and preserve:

IDENTIFICATION
- session ID;
- project ID;
- start and close time;
- objective;
- final status.

EXECUTION
- what was done;
- what was not done;
- last valid progress;
- files and outputs;
- commands and tools used.

DECISIONS
- decisions;
- rationale;
- status DRAFT/CANON;
- approvals.

VALIDATION
- checks performed;
- evidence;
- errors found;
- errors corrected;
- errors pending.

CURRENT STATE
- current focus;
- next action;
- blockers;
- risks;
- assumptions;
- dependencies;
- Git state;
- evidence freshness and confidence.

WORK MEMORY
- backlog;
- technical debt;
- project ideas;
- cross-project ideas;
- general or unrelated ideas;
- new-project opportunities;
- reusable learning;
- Skill candidates;
- GRC candidates.

CONTINUITY
- exact resume instructions;
- required context and files;
- recommended AI/tool;
- context and sharing policy.

12.60_DEGRADED_CLOSE
A dirty or incomplete session may close only when:
- changes are identified;
- recovery or backup exists;
- unresolved state is explicit;
- the next action is executable;
- final state is marked DEGRADED.

A degraded close must never be represented as clean.

12.70_OUTPUT_RELATIONSHIPS
- SESSION.CLOSE is the machine-readable close record.
- BATON is a compact operational handoff.
- CURRENT_STATE is the current operational truth.
- WHOAMI is a generated human-readable projection.
- Detailed registers remain authoritative for backlog, decisions, debt and ideas.

Session and continuity readers must be project-scoped.

Operational source precedence:
CURRENT_STATE -> project BATON -> project BACKLOG.

Session source:
04_PROJECTS\<PROJECT_ID>\ARTIFACTS\SESSION.ACTIVE.json

A context reader must not create, close or mutate a project session.

14.00_B3_B2B1_MAINTENANCE_WRAPPER_POLICY
================================================================================

HIA_TOL_0041_Start-Session.ps1 and HIA_TOL_0042_Close-Session.ps1 are legacy
compatibility adapters.

They must:
- require an explicit ProjectId;
- delegate to HIA_PROJECT_ENGINE.ps1;
- operate only on project-scoped session state;
- report that Git mutation, RADAR execution and push were not performed.

They must not:
- create or switch branches;
- execute git add, git commit or git push;
- execute RADAR as a side effect;
- mutate HUMAN.README doctrine;
- mutate HUMAN.README\04.0_HUMAN.BATON.txt;
- implement a competing global session lifecycle.

The authoritative project runtime functions are:
- Start-HIAProjectSession;
- Get-HIAProjectSessionStatus;
- Close-HIAProjectSession.

Full SESSION.CLOSE generation remains a separate governed implementation step.
